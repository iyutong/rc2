## 订阅覆盖面盘点（23:05，结论性认识）

当前只有 3 条数据通路，不是全量抓包：
1. 摇杆：`transact(4)` **主动轮询**（每 40ms），`pack` 里 cmdSet=6/cmdId=-1，走 pull，不经过 `probe()`。
2. 按键：`transact(2)` filter `{4,2,0,6,6,174}`，只订 6/174。
3. 通配试探：`transact(2)` filter `{4,2,0,6,6,-1}`，仅 cmdSet=6 下不限定 cmd，是否被服务端当通配未验证。

三层盲区：
- cmdSet 层固定为 6，其他 cmdSet 完全收不到。
- cmdId 层只明确订了 174，其余依赖 -1 通配（有效性未知）。
- 类型层：`onPush` 派发按键要求 `hdr[5]==2`，6/174 的其他 type 只进探针页不进按键解析。

**关键认知：探针页不是全量抓包。** filter 在 DJI 服务端执行，未放行的包不会进入 App 进程，`probe()` 看不到。签名表是幸存者集合。
判断通配是否生效：看签名表里是否出现 cmd 非 174 的 `6/xxx` 行；`modeSource` 显示 17B 飞行模式包来源。

## 服务不支持 -1 通配 → 改为 cmdId 枚举（23:30，已编译通过）

用户明确：protocol 服务不支持 -1 匹配。上一版 `full`(`-1/-1`) 与 `wide`(`6/-1`) 都拿不到数据，全部删除。

### 新方案：逐个精确订阅试探
- `McuReader.startCmdProbe(cmdSet, from, to)`：**独立线程**（`rc2-cmd-probe`，MIN_PRIORITY）遍历 cmdId；**不能放 worker**——几千次 Binder 调用会把 40ms 的摇杆轮询卡死。
- 每个 cmdId：`trySubscribe()` 用 filter `{4,2,0,6,6,cmdId}` + 共用 `sink` Binder 订阅，`reply.readException()` 不抛异常即视为该 cmd 存在 → `InputMonitor.cmdHit(id)` → 成功才 `dropSink()`（transact 5）退订再下一个。
- 失败不 drop，省一半调用。
- `sink` 的 `onTransact` 读完 15 个 int + byte[] 后丢弃，不参与统计。
- 进度 `cmdCursor` 每 64 个 cmd 推进一次 revision；结束按 `cmdCursor >= to` 判「已完成 / 已中止」。

### UI（page_scan.xml 改为 cmd 枚举页）
- 标题「cmd 枚举」，摘要 `状态 · 已扫/总数 · 命中 N · 耗时 ms`，右上「开始扫描 / 停止」。
- 命中列表按 6 列网格显示 `6/xxx`（薄荷色）。
- 若命中数 == 总数，页面提示「服务端不校验 cmd 是否存在，此路无法区分」。
- 不再进页面自动订阅，改为手动触发（枚举是重操作）。
